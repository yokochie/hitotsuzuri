# ひとつづり — Phase 2以降の設計・実装計画

## 1. 目的と前提

選んだ4枚を、noteの記事とリール用動画に仕上げる作業を毎週続けられるようにする。

Phase 1は2026-11-04時点で完了との報告を受けている。本書はPhase 1設計書の後続計画を具体化した提案であり、完成したリポジトリ、保存形式、テスト結果は未確認。実装開始時は実コードを正として、名称、モデル、保存先、対応OS、依存関係を照合する。既存データの移行が必要なら先に計画する。

本書中の値は初期提案。AI-DLCのInceptionで確認し、決定記録を残す。アプリ開発にAI-DLCを使うことと、製品内に生成AI機能を搭載することは別であり、文章生成APIは初期必須機能にしない。

## 2. 全体ロードマップ

| 段階 | 到達点 | 主な出力 |
|---|---|---|
| Phase 1（完了） | アルバムから4枚を選択・確定 | 選択セッション |
| Phase 2 | noteへ手動で移せる記事と画像を作る | 記事Markdown、画像4枚、マニフェスト |
| Phase 3 | 同じ4枚から縦型動画を作る | MP4、動画設定 |
| Phase 4 | 毎週の制作と履歴管理を支える | 制作一覧、成果物履歴、リマインダー |

推奨順はPhase 2 → Phase 3 → Phase 4。各Phaseの必須部分を先に完成させ、拡張機能は別の実装単位にする。全Phaseを一度に実装しない。

## 3. 共通設計

### 3.1 制作物の単位

Phase 1の選択セッションから「制作プロジェクト」を作成する。選択元のアルバムID・写真IDだけでなく、当時のアルバム名、順序、作成日時もスナップショットとして保持する。

| データ | 保持内容 |
|---|---|
| 制作プロジェクト | ID、元セッションID、作成日、更新日、選択リビジョン |
| 選択写真 | 写真ID、順序、キャプション、代替テキスト |
| アルバム情報 | 元の名前、撮影日候補、場所・機材などの手動入力 |
| 記事下書き | タイトル、導入、各写真への文章、結び |
| 動画設定 | 寸法、fps、表示時間、画像配置、テロップ、音声設定 |
| 成果物履歴 | 種類、作成日時、入力リビジョン、保存先、結果 |

既存のCodable保存を使えるなら継続する。履歴件数や検索の必要性を確認してからSwiftDataなどへの変更を判断する。保存形式には`schemaVersion`を付け、旧形式の読込テストを用意する。

```swift
import Foundation

// 設計意図を示す参考モデル。既存実装に合わせて調整する。
struct ArticleDraft: Codable, Equatable {
    var title: String
    var introduction: String
    var captions: [String] // 写真IDとの対応は実装で明示する
    var closing: String
}

struct ExportManifest: Codable {
    var schemaVersion: Int = 1
    let projectID: UUID
    let selectionRevision: Int
    let createdAt: Date
    let orderedAssetIDs: [String]
    let relativeImagePaths: [String]
    let articleRelativePath: String
}
```

### 3.2 共通サービス

- `AssetExportService`：PhotoKitから現在の編集結果を取得し、用途に合わせて画像化する。
- `ProjectRepository`：制作プロジェクトと下書きを保存する。
- `ExportCoordinator`：進捗、キャンセル、失敗、完了を管理する。
- `OutputLocationService`：ユーザーが指定した保存先へのアクセスを管理する。
- `MetadataParser`：アルバム名から撮影日などの候補を抽出する。

画像取得・レンダリング・書き出しはUI更新から分離する。SwiftUIへ公開する状態はMainActorで更新する。既存Repositoryと責務が重複する場合は再利用する。

### 3.3 写真の取得と出力

- サムネイルを成果物に流用せず、用途に必要な解像度をPhotoKitへ要求する。
- 原則は写真アプリでの現在の編集結果を使う。未編集原本への切り替えは拡張とする。
- iCloud上のみの写真にはネットワーク取得、進捗表示、キャンセルを実装する。
- 回転情報を反映し、HEIF・RAW等は互換性のあるJPEGへレンダリングする。Live Photoは静止画として扱う。
- 元写真を変更しない。位置情報など不要なメタデータは出力画像にコピーしない。
- 一時領域で完成させ、成功時に成果物として確定する。失敗・キャンセル時は成功扱いにせず、当該ジョブの一時ファイルを片付ける。
- 同名出力は連番やUUID付きの別フォルダにし、既存成果物を無断で上書きしない。
- 書き出し中の設定はスナップショットに固定し、別の編集によって処理中の内容が変わらないようにする。

Sandbox外への書き出しは保存パネルで選択した場所を使う。再起動後もアクセスを継続する場合のみsecurity-scoped bookmarkを保存し、無効になった場合は再選択してもらう。

## 4. Phase 2 — note記事作成支援

### 4.1 到達点

4枚の写真と文章の下書きをアプリ内で整え、noteへ手動で移せる出力一式を作る。Markdownをnoteへ直接インポートできることは前提にしない。記事本文のコピーと画像の手動アップロードを基本の受け渡し方法とする。

### 4.2 必須機能

- [ ] 確定済みセッションから制作プロジェクトを作る
- [ ] 4枚のプレビューと順序を表示する
- [ ] タイトル、導入、各写真への文章、結びを編集する
- [ ] 下書きを保存・再開する
- [ ] アルバム名の末尾`@YYMMDD`から撮影日候補を抽出する
- [ ] 撮影日候補を確認・修正・削除できる
- [ ] 場所、機材、フィルム、人物名を手動入力できる
- [ ] 画像4枚とMarkdownをフォルダへ書き出す
- [ ] noteへ貼り付ける文章をプレーンテキストでコピーする
- [ ] 書き出したフォルダをFinderで開ける
- [ ] 取得・書き出しの進捗、失敗理由、再試行を表示する

### 4.3 UIと操作フロー

1. 選択確定画面から「記事を作る」を開く。
2. 左に4枚のプレビュー、右に記事編集フォームを表示する。
3. 撮影日候補と元アルバム名を確認する。
4. テンプレートを入力し、下書きを保存する。
5. プレビューを確認して「記事と画像を書き出す」を実行する。
6. 本文をコピーし、noteの編集画面へ手動で貼り付け、画像を挿入する。

初期テンプレートは空欄を含む定型文とし、撮影事実や人物情報を自動で創作しない。自由編集済みの本文を、テンプレートの変更で上書きしない。

### 4.4 アルバム名の解析ルール

例：`御代田 PENTAX 6x7 Portra 160@260913`

- 末尾が`@`と6桁の数字であれば日付候補として解析する。
- 初期ルールでは`YY`を2000〜2099年に対応させ、画面に候補であることを表示する。
- `260913`は2026-09-13の候補になる。
- `260231`のような存在しない日付は、自動補正せず未解析として扱う。
- 撮影日はタイムゾーンでずれない年月日として保存する。日時が必要なモデルとは分ける。
- 接尾辞を除いた文字列をタイトル候補にする。
- 名前の残りを空白で機械的に分割して、人物・場所・機材を確定しない。辞書による候補提示は後続拡張とする。

### 4.5 出力仕様

```text
hitotsuzuri-20260913-<短いID>/
├── article.md
├── manifest.json
└── images/
    ├── 01.jpg
    ├── 02.jpg
    ├── 03.jpg
    └── 04.jpg
```

- ファイル名は写真の順序に対応させる。
- Markdown画像パスは相対パスにする。
- 初期画像設定案：sRGB、JPEG品質0.9、長辺2560px以下、元画像より拡大しない。
- 設定値はnoteの必須仕様ではなく、互換性と画質のためのアプリ側の初期値とする。
- マニフェストに写真ID、順序、プロジェクトID、作成日、選択リビジョンを記録する。
- マニフェストはローカル管理用で、noteにアップロードする対象には含めない。
- 画像取得が1枚でも失敗した場合は、4枚セットの書き出し成功とは表示しない。

記事の初期構造：

```markdown
# 記事タイトル

導入文

![写真1の代替テキスト](images/01.jpg)

写真1への文章

<!-- 写真2〜4も同じ構成 -->

結びの文章
```

### 4.6 実装順序

1. 既存選択セッションの読込と制作プロジェクトの保存を実装する。
2. メタデータ解析と手動修正フォームを実装する。
3. 下書き編集・自動保存・再開を実装する。
4. 1枚の画像を指定サイズへ書き出す技術検証を行う。
5. 4枚の順序付き書き出しとMarkdown生成を統合する。
6. 保存パネル、本文コピー、Finder表示を実装する。
7. iCloud、削除済み写真、容量不足、キャンセルを確認する。

### 4.7 受け入れ条件

- [ ] Phase 1で選んだ4枚が同じ順序で記事に対応する
- [ ] 下書きがアプリ再起動後も復元される
- [ ] 有効な日付だけを候補化し、手動修正できる
- [ ] 出力Markdownの画像参照先がすべて存在する
- [ ] 画像の回転と写真アプリ側の編集結果が反映される
- [ ] 出力画像に位置情報が含まれないことを確認する
- [ ] iCloud取得中にキャンセルしても不完全な成功成果物が残らない
- [ ] 本文コピーと画像アップロードで、実際にnoteの下書きへ移せる
- [ ] 前回の成果物を上書きせずに再出力できる

### 4.8 後続拡張

複数テンプレート、ハッシュタグ候補、任意の生成AIによる文章補助、noteへの直接連携。直接連携は実装時点の公式仕様を調査し、認証・投稿方法が成立する場合に別途設計する。非公開APIやブラウザ自動操作を初期計画の前提にしない。

## 5. Phase 3 — リール用動画生成

### 5.1 到達点

選択した4枚を同じ順序で並べ、縦型MP4として保存できる。初期版は無音・静止表示で完成させ、その後にトランジション、動き、テロップ、BGMを追加する。

### 5.2 初期仕様案

| 項目 | 初期値 |
|---|---|
| 画面 | 1080 × 1920、9:16 |
| フレームレート | 30fps固定 |
| コーデック・形式 | H.264、MP4 |
| 色 | SDR、sRGB入力から適切に色変換 |
| 表示時間 | 1枚3秒、4枚で12秒 |
| 画像配置 | 全体表示（aspect fit）、無地背景 |
| 音声 | なし |
| 並び順 | 制作プロジェクトの4枚の順序 |

これらはアプリの出力プリセットであり、投稿先の最新の入稿要件を保証する値ではない。投稿先へのアップロードは手動とし、公開前に実機で確認する。

### 5.3 画像配置

- 初期値は写真全体を見せる配置とし、横位置写真も切り落とさない。
- 拡張で全面表示（aspect fill）とトリミング位置の指定を追加する。
- 配置は写真ごとに保持し、プレビューと出力で同じ計算を使う。
- テロップには余白を持たせる。投稿先UIの固定セーフエリアは保証せず、必要なら余白を調整可能にする。

### 5.4 技術構成

| 責務 | 候補 |
|---|---|
| フレーム描画 | Core Graphics / Core Image |
| フレーム書込 | AVAssetWriterとピクセルバッファ入力 |
| 音声・映像合成 | AVMutableComposition、AVAssetExportSession |
| プレビュー再生 | AVPlayer、SwiftUI VideoPlayer |
| 設定保持 | 既存のProjectRepository |

対象SDKで利用できるAPIと非推奨状況を実装時に確認する。静止画4枚を1本の動画にする小さな技術検証を先に実施し、成立した方式を採用する。

### 5.5 レンダリング設計

全フレームをメモリに保持せず、出力時刻に必要なフレームを順次描画する。時刻はフレーム番号から計算し、浮動小数点の加算によるずれを避ける。

```swift
import CoreMedia

struct ReelTimeline {
    let fps: Int32
    let framesPerPhoto: Int
    let photoCount: Int

    var totalFrames: Int { framesPerPhoto * photoCount }

    func presentationTime(for frame: Int) -> CMTime {
        CMTime(value: Int64(frame), timescale: fps)
    }

    func photoIndex(for frame: Int) -> Int {
        min(frame / framesPerPhoto, photoCount - 1)
    }
}
```

この例は無音・トランジションなしの基本タイムライン。初期化時にfps・写真枚数・表示フレーム数を正数として検証する。書き込み先の受け入れ状態、キャンセル、終了時刻、最終フレーム、writer完了エラーを実装で処理する。

### 5.6 段階的な実装

#### Phase 3A — 必須版

- [ ] 4枚を無音の縦型MP4にする
- [ ] 表示時間と背景色を設定できる
- [ ] 動画をアプリ内で再生する
- [ ] 進捗、キャンセル、再試行を提供する
- [ ] 書き出し設定と入力リビジョンを履歴へ保存する

#### Phase 3B — 演出

- [ ] クロスフェードを追加する
- [ ] ズーム・パン（Ken Burns効果）を写真ごとに設定する
- [ ] タイトル、撮影日、クレジットを任意表示する
- [ ] 表示時間とトランジションの重なりを含めて総尺を表示する
- [ ] 日本語の長文、改行、文字切れを確認する

トランジションを追加する際は「総尺を固定するか、重なり分だけ短くするか」を先に決め、プレビューと書き出しで統一する。

#### Phase 3C — 音声

- [ ] ユーザー指定のローカル音声を読み込む
- [ ] 開始位置、音量、フェードイン・アウトを設定する
- [ ] 長い音声は動画尺で切り、短い音声は初期仕様では無音で補う
- [ ] 音声ファイルの参照切れから復旧できる

BGMの自動取得は行わない。投稿先の音源機能を使うため、無音動画の出力は常に残す。

### 5.7 受け入れ条件

- [ ] 出力が1080 × 1920、30fpsのMP4として再生できる
- [ ] 初期設定で総尺が12秒となり、最後の写真も指定時間表示される
- [ ] 写真順、回転、配置、色の見え方を実画像で確認する
- [ ] 写真全体表示では横写真の端が切れない
- [ ] キャンセル・容量不足・writer失敗が成功扱いにならない
- [ ] 再出力で既存ファイルを上書きしない
- [ ] 同じ設定のプレビューと最終出力で配置が一致する
- [ ] QuickTime Playerと実際の投稿先で手動検証する
- [ ] 演出・音声を追加した場合は総尺、音量、文字表示も検証する

## 6. Phase 4 — 週次制作と履歴管理

### 6.1 到達点

毎週アプリを開くと、制作候補、途中の下書き、作成済み成果物が分かり、過去の制作も再開できる。

### 6.2 制作状態

記事と動画は独立した状態として管理する。

| 種類 | 状態の例 |
|---|---|
| 記事 | 未着手、編集中、書き出し済み、公開済み（手動） |
| 動画 | 未着手、設定中、書き出し済み、投稿済み（手動） |
| 処理ジョブ | 待機、実行中、成功、失敗、キャンセル |

ファイルを書き出しただけでは公開済み・投稿済みにしない。ユーザーが明示的に記録した場合のみ公開状態を変える。任意で公開URLと公開日を保存する。

写真順や文章、動画設定を変更したら、過去の成功成果物は履歴として保持し、現在の入力に対して再出力が必要であることを表示する。写真変更時には記事内の写真対応を写真IDで維持し、削除・追加された写真の文章を確認してもらう。

### 6.3 候補表示

- 指定フォルダ配下から、制作未着手のアルバムを候補表示する。
- 撮影日候補または写真の撮影日で並べ替える。日付不明は別表示する。
- アルバム名の日付と、アプリが初めて見つけた日時を分けて保存する。
- 「前回以降に追加された候補」は初回検出日時で判定する。
- 古い写真を今週取り込んだケースも取りこぼさない。
- 一度制作したアルバムも、別の4枚で新規制作できる。
- 候補からの除外・除外解除を提供する。

### 6.4 リマインダー

- [ ] 曜日と時刻をユーザーが選ぶ
- [ ] 通知を有効にするときに権限を要求する
- [ ] UserNotificationsによるローカル通知を予約する
- [ ] 設定変更時は既存の同一通知を更新し、重複予約を防ぐ
- [ ] 無効化時は対象通知を取り消す
- [ ] タイムゾーン変更時の挙動を検証する
- [ ] 通知から制作一覧を開ける

初期版の通知は「今週の4枚を選びませんか」のような静的な案内とする。アプリ終了中のライブラリ走査や、未処理件数の自動更新、動画生成は約束しない。スリープや通知設定によって配信が遅れる可能性を踏まえ、起動時にも制作状況を表示する。

### 6.5 履歴とデータ保護

- 下書きはアプリ内の永続領域へ保存し、一時キャッシュと区別する。
- 書き出し先が見つからない場合も制作履歴を消さない。
- 保存先の再指定、Finder表示、再書き出しを用意する。
- 写真IDが無効になった場合は再選択を促す。
- 元写真が消えても過去の文章は保持する。出力画像が残っている場合に再利用するかはユーザーが選べるようにする。
- プロジェクトデータのバックアップ・復元機能は履歴機能の後に追加する。写真本体が含まれるかを明示する。

### 6.6 受け入れ条件

- [ ] 未着手・編集中・書き出し済みの制作を一覧で識別できる
- [ ] 記事だけ完了、動画だけ完了という状態を保持できる
- [ ] 同一アルバムから複数の制作を作れる
- [ ] 入力変更後に成果物が古くなったことを判定できる
- [ ] 起動し直しても履歴と下書きが保持される
- [ ] 通知の有効化・変更・解除で重複が生じない
- [ ] 通知拒否時にも制作機能を使える
- [ ] 保存先や元写真が消えても既存の文章を失わない

## 7. 横断的なテスト計画

| 対象 | 主な検証 |
|---|---|
| メタデータ解析 | 正常日付、閏日、不正日付、接尾辞なし、日本語・空白 |
| 永続化 | 旧データ移行、再起動、途中保存、破損データからの案内 |
| 画像出力 | 縦横、回転、HEIF、RAW、編集済み、iCloud、位置情報除去 |
| 記事 | 写真と文章の対応、特殊文字、相対リンク、本文コピー |
| 動画 | 寸法、フレーム数、尺、最終フレーム、色、クロップ、再生 |
| 失敗時 | キャンセル、権限取り消し、容量不足、保存先参照切れ |
| 週次運用 | 古い写真の新規取込、同一アルバム再制作、通知更新 |

ロジックは単体テスト、ファイル書き出しは一時ディレクトリを使った統合テストで検証する。写真アプリ、iCloud、Sandbox、note、投稿先の実際の挙動は手動チェックとして記録する。動画はメタデータ検査だけでなく再生・見た目も確認する。

## 8. AI-DLCでの実装単位案

| Unit | 内容 | 前提 |
|---|---|---|
| U1 | 既存実装の照合、制作モデル、保存形式移行 | Phase 1 |
| U2 | 下書き編集、メタデータ候補 | U1 |
| U3 | 画像・記事の書き出し | U1、U2 |
| U4 | 無音の動画レンダリングと再生 | U1、U3の画像取得基盤 |
| U5 | 動画演出 | U4 |
| U6 | 任意音声 | U4 |
| U7 | 制作一覧、成果物履歴、候補表示 | U3、U4 |
| U8 | 週次リマインダー | U7 |

Phase 2はU1〜U3を対象とする。Phase 3開始時にU5・U6を同時に含めるか改めて決める。Phase 4はU7〜U8を対象とする。各Unitの完了時に受け入れ条件と証拠を記録する。

## 9. Inceptionで確定する項目

- [ ] 完成したPhase 1のモデル、保存形式、対応OS、テスト方法
- [ ] 既存データを引き継ぐ方法と移行対象
- [ ] Phase 2の初期テンプレートと画像出力設定
- [ ] 写真順変更の操作場所と、記事・動画への反映ルール
- [ ] 動画の背景、表示時間、演出・BGMを含める段階
- [ ] 公開状態を手動管理するUI
- [ ] 通知の初期設定とタイムゾーン変更時の扱い

未確定事項には提案値を提示し、実装への影響が大きい選択だけ確認する。Phase 3・4の未確定事項によってPhase 2全体を止めない。
