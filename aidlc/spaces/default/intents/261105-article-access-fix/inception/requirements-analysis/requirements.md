# 記事を開けない問題の修正要件

## Intent Analysis
本人が確定した写真4枚から記事編集へ進み、文章を保存・再開できる状態を回復する。元の依頼は「記事を開こうとしたところ画像のようなメッセージが出て開けませんでした。修正したいです」。現在の画面はアクセス許可エラーを表示している。

調査では、写真取得前の記事一覧読込で保存先の全祖先を読取openする処理へ到達することを確認した。許可済み保存先に不要な祖先読取権限を要求している可能性がある。これは原因候補であり、本人の実機で失敗したsyscall・errnoは未観測である。実装前に回帰試験で候補を検証し、別の原因なら証拠に基づき修正する。

## Sources
- S1: 初期依頼。`project-description.json`（`aidlc engine workspace project-description`で取得）。
- S2: 本人提供画像のエラー表示と再試行ボタン。
- S3: `aidlc/spaces/default/codekb/hitotsuzuri/business-overview.md`（本人用途・写真選択から記事への流れ）。
- S4: 同ディレクトリの`architecture.md`（読込順・共通保存処理）と`code-structure.md`（影響する領域）。
- S5: 同ディレクトリの`code-quality-assessment.md`（原因候補、安全性、既存fixtureの不足）。
- S6: 本チャットの本人方針「ローカルだと承認しなければならずリモートで開発しにくいので、実行機会をできれば減らしたいです」。既に合意したCI優先と実機確認の集約を継続する。
- S7: `aidlc/spaces/default/memory/team.md`と`project.md`の既存データ保護・TDD・製品全体80%以上・統合前CI・写真非変更の条件。

## Functional Requirements

### FR1 許可された保存先で記事を開く — Must
保存先への必要なアクセスが許可されている場合、祖先ディレクトリの列挙権限や既存祖先への作成権限を追加要求せず、確定選択から記事を開けること。（S1–S5）

- Given 写真4枚の確定選択があり、許可された保存先に記事がない、When 記事を開く、Then 現行仕様どおり新規記事へ進み、保存して再開できる。
- Given 同じ選択に対応する保存済み記事がある、When 記事を開く、Then 保存済み本文・写真順序・識別子を保持して再開できる。
- Given 末端の保存先は必要な読書きが可能で、祖先には検索のみ可能・読取不可のディレクトリがある、When 記事を一覧・作成・保存・再開する、Then 祖先の読取不能だけを理由にpermissionDeniedにならない。
- Sandbox有効な通常Application Support経路で、合成データを用いた記事開始・保存・再開の検証を行う。合成一時rootの成功だけで通常保存先の保証としない。具体的な隔離方法は実装計画に記す。

### FR2 本当のアクセス拒否を安全に扱い再試行できる — Must
保存先に必要なアクセスがない場合は失敗として返し、回復後に同じ操作を再試行できること。（S1、S2、S5、S7）

- Given 保存先の必要な権限が失われた、When 記事を読込・保存する、Then 成功や空一覧へ置換せず、現行の型付き失敗と画面の再試行導線を維持する。
- Given 失敗前に記事または確定選択が保存されている、When アクセスが拒否される、Then 元データを削除・初期化・上書きしない。
- Given 権限が回復した、When 再試行する、Then アプリ再起動を必須とせず記事操作を再開でき、再試行による記事重複や本文の欠落がない。

### FR3 共通処理の利用者を壊さない — Must
記事保存と同じディレクトリ操作を使う1枚検証出力・4枚出力・回復journal・Finder前検査の正常動作と既存の保護契約を維持すること。（S4、S5、S7）

- Given 書込許可済み保存先、When 既存の出力操作を行う、Then 保存済み入力・画像順序・既存出力形式を保持して成功する。
- Given 取消、中断、競合、他者ファイル混在、When 既存の回復処理を行う、Then 所有を確認できないファイルを削除せず、既存の競合・結果不明の扱いを維持する。
- 詳細な保存・出力仕様は既存仕様を継続し、新機能は追加しない。変更が波及する共通helperの利用者を実装計画と回帰検証へ対応付ける。

## Non-Functional Requirements

### NFR1 権限とファイルの安全性 — Must
App Sandbox・現在のentitlementsを維持し、今回の修正のためにOS権限・ファイル権限を拡張しない。symlinkの中間成分・末端を拒否し、ディレクトリ差替え防御・fd相対操作・排他・原子的確定を維持する。関連保護試験の成功と設定差分確認を合格条件とする。写真ライブラリの変更と画像取得の通信は追加しない。（S4、S5、S7）

### NFR2 再現可能な回帰と統合前CI — Must
今回の不具合を検出する最小の回帰を先に追加し、意図した失敗→最小修正後の成功を記録する。全既存機能試験の成功と全製品行coverage80%以上を統合前CIで確認する。測定対象の除外や閾値引下げで通さない。CI優先で実施し、同じ目的のローカルUI試験は反復しない。試験の配置・正確なコマンド・実行回数の抑制は実装計画で具体化する。（S5–S7）

### NFR3 実機確認とプライバシー — Must
自動試験は隔離した合成選択・記事・画像を使い、本人の実写真・保存データ・一般クリップボード・OS設定を変更しない。本人環境で「選択→記事を開く→保存→再開」を確認する手順を一度にまとめる。自動試験で検証した環境と本人確認済み/未確認を区別し、実機未確認をCI成功で補完しない。（S2、S5–S7）

## Constraints
- 現行macOS/Swiftアプリ・記事保存形式・選択との対応付けを継続する。データ移行・保存先の強制変更・再インストール・既存データ削除を修正の前提にしない。
- 本人確認が必要な要件・実装計画は承認を受けてから製品変更を行う。現在は調査・要件のみで製品コード未変更。
- 自動試験の具体的なコマンドは実装計画で定める。ローカルUIが避けられない場合は理由を示して本人へ確認する。
- Phase2の既に受容された未確認項目を、本修正の成功によって解消済みへ変更しない。

## Assumptions & Open Questions
要件の成立に必要な未承認の仮定はない。技術的な検証事項として、祖先の読取openが本人の実機エラーの直接原因かは未確定である。回帰試験とSandbox経路の検証で切り分け、再現できなければ未確定と報告して次の調査を行う。修正済みの判定には、技術的回帰の成功と本人環境の確認状況の明示が必要である。

## Out of Scope
画面全体の作り直し、エラーメッセージ体系の全面改訂、OS設定変更、Sandbox解除、追加entitlements、写真認可の強制リセット、データ移行、クラウド・自動投稿、性能再測定の一式反復、既存Phase2の全未確認項目の再実行は含めない。原因調査で必要性が判明した追加変更は、根拠と影響を示して扱う。
