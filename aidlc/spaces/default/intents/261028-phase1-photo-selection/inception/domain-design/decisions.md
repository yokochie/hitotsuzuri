# ひとつづり — 設計判断

入力: [要件](../requirements-analysis/requirements.md)、[ストーリー](../user-stories/stories.md)、[開発規約](../practices-discovery/team-practices.md)、[確認済み方針](domain-design-questions.md)。構成の正本は[components.md](components.md)。各判断は本段階の承認対象。

## ADR-001: 5つの責務へ分割する

### Context

4枚制限、確定検証、保存失敗、欠損復元、画像の遅延応答をTDDで確認する必要がある。

### Decision

画面・進行・ライブラリ参照・画像取得・保存の5つを論理的に分ける。画面は進行担当に操作を渡し、進行担当が下位の3担当を呼ぶ。

### Consequences

個別にFakeへ置き換えて失敗を再現できる。境界と結果の変換は増える。依存は循環させず、別プロセスや配布方式はここで決めない。

### Alternatives Rejected

3分割は初期の接続が少ないが、画面とルール、探索と画像寿命の変更が結びつく。各Viewへの判断分散はさらに状態不整合とルール重複を増やす。今回は5分割を本人が選択した。

### Security and Compliance

下位境界にライブラリ変更を提供せず、画像取得通信を要求しない。個人写真を外部送信・恒久複製しないという合意を維持する。

## ADR-002: 編集状態と永続化された確定内容の所有者を分ける

### Context

編集中の変更で前回確定内容を失わず、保存失敗でも以前のデータを保つ必要がある。

### Decision

進行担当が編集と検証状態を所有し、保存担当が永続化された設定と確定内容を所有する。保存成功後だけ進行側の保存済みの写しを更新する。復元の有効性判断は進行担当に一元化する。

### Consequences

画面の未保存・保存済み表示が一貫する。保存要求の世代と成功内容の照合が必要になる。詳細な形式・型・原子性は後の設計で定める。

### Alternatives Rejected

編集配列を直接自動保存する案は未確定の選択を保持してしまう。保存担当がライブラリ検証まで行う案はPhotosと永続化の責務・依存を結びつけ、復元と確定の判断を重複させる。

### Security and Compliance

永続化対象は設定と参照等のみとし、画像本体は対象外。破損や権限喪失で保存済み内容を自動破棄しない。
