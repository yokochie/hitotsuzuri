# Phase2の対象範囲

## 入力と目的
`../intent-capture/intent-statement.md` の本人向け週次記事制作を対象とする。実現性・制約は `../feasibility/feasibility-assessment.md` と `../feasibility/constraint-register.md`、リスクは `../feasibility/raid-log.md` を引き継ぐ。追加の範囲と優先順位は `scope-definition-questions.md` Q1〜Q3と要約確認に基づく。

## 必須の範囲
| ID | 利用者ができること | 完成の判断 | 根拠 |
|---|---|---|---|
| SC1 | Phase1で確定した4枚を、同じ順序で記事制作に引き継ぐ | 4枚と記事の対応・順序を確認でき、既存選択データを失わない | intent-statement、feasibility-assessment |
| SC2 | 記事の下書きを編集・保存・再開する | 再起動後も文章と写真の対応を復元できる | intent-statement |
| SC3 | アルバム名末尾から撮影日候補を確認する | 候補の確認・修正・削除ができる。具体的な解析規則は要件で確定する | 本段階Q1 |
| SC4 | 場所・機材・フィルム・人物名を手動入力する | 本人が入力・編集でき、撮影事実や人物情報を自動で創作しない | 本段階Q1 |
| SC5 | 画像4枚とMarkdownを書き出す | 4枚が順序どおり対応し、本文から画像を参照できる。1枚でも失敗すれば全体成功と扱わない | intent-statement、feasibility-assessment |
| SC6 | 本文をコピーし、noteへ手動で移す | コピーした本文と書出した画像を使い、本人がnoteの下書きへ移せる | intent-statement |
| SC7 | Finderで出力フォルダを開く | 書出し成功後に、その成果物の場所を開ける | 本段階Q2 |
| SC8 | 失敗・取消から安全にやり直す | 原因と次の操作が分かり、不完全な成果物を成功扱いせず、旧データと既存成果物を保護する | intent-statement、constraint-register |

## 共通の制約
- 画像取得の通信は要求しない。写真アプリで事前ダウンロードし、取得できない場合は案内する。写真ライブラリを変更しない。
- 本人のMacでの個人利用とする。追加の外部連携や有料サービス・ツールは前提にしない。
- 要件と実装計画の本人確認後に実装する。TDD、80%以上の行カバレッジ、統合前CIの条件を維持し、具体的な対象と実行環境は計画で明らかにする。
- 既存の選択データとの互換性、記事用画像の取得・品質、Sandboxから保存先へのアクセスは検証が必要。画像設定・保存方式・正式な実装単位は本段階で技術仕様として確定しない。
- 固定期限・特別な予算枠・作業停止事情はない。Phase1の過去のCI例外をPhase2の免除にはしない。

## 今回の対象外
- Phase3の動画生成、演出、音声。
- Phase4の制作履歴一覧・候補表示・通知。
- 生成AIの文章補助、noteへの自動投稿・直接連携。
- 外部公開、独自クラウド機能、画像取得の通信。
- Phase1の既知問題すべての修正を今回の約束に含めること。既知問題・未確認は保持し、新規回帰と阻害要因は別に扱う。

## 優先順位と依存
最初に既存選択の引継ぎと画像1枚の書出しを小さく検証する。最小の一連の操作を確認してから、下書き・撮影情報・4枚出力・受渡し・例外処理を完成させる（本段階Q3）。下書き画面を先に全て完成させてから画像取得の成立性を調べる順序は採用しない。

利用の流れは「確定済み4枚を開く → 日付候補を確認し文章・撮影情報を整える → 下書きを保存・再開する → 記事と画像を書き出す → 本文をコピーしFinderで画像を確認する → noteへ手動で移す」。失敗・取消時は成功へ進めず、文章・旧成果物を保持して再試行する。これは利用者の流れであり、正式な実装単位や構造の決定ではない。

## 完了条件と未確定事項
SC1〜SC8を要件・受け入れ条件と試験へ具体化し、自動確認と本人の実機確認を分けて証拠を残す。画像用設定、日付の詳細規則、保存方式、再開の導線、実装単位、CI実行環境は後続の要件・設計・計画で確定する。検証で成立しない点があれば、範囲や品質基準を無断で下げず本人へ示す。
