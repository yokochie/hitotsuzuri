# 下書き復帰後の写真表示の修正要件

## 意図と根拠

本人が保存済みの記事を再開し、写真4枚を確認しながら編集と出力を続けられるようにする。

初期依頼: 下書きから復帰すると写真4枚が画像の取得待ちのままで、再試行しても表示されない。出力は写真アプリで読み込み後に成功した。下書き復帰時の画像表示の不具合を調査・修正する。

本人の画像と回答から、4枚の「画像の取得待ち」と再試行無反応を確認した。出力成功の報告は表示画像取得の成功とは区別する。

上流の `../../../../codekb/hitotsuzuri/business-overview.md`、`architecture.md`、`code-structure.md` を参照した。詳細根拠は同じCodeKBの `code-quality-assessment.md` と `../reverse-engineering/developer-scan.md`。出力前に表示用画像を破棄し、その後復元しない経路を静的に確認したが、本人がその経路を通ったかは未確定。既存の保存先アクセス修正を今回の原因とは扱わない。

## 機能要件

全てMust。以下の「取得可能」は、通信せずPhotosが表示用画像を返せる状態を指す。写真がローカルで利用できない場合の成功を保証しない。

### FR1 下書き再開で4枚の取得を開始する

- Given 保存済み下書きと取得可能な4枚がある。When アプリ再起動後または写真選択画面から下書きを再開する。Then 保存された順序で4枚の取得が開始され、各画像が表示される。
- Given 写真の一部を取得できない。When 下書きを再開する。Then 取得可能な画像は表示し、取得できない番号は失敗・期限超過等の実際の状態を文字で示す。取得処理が存在しないまま全番号を無期限の「取得待ち」にしない。
- 検証: 合成画像の要求発行と4枚の実表示、および一部失敗時の状態を確認する。新しいセッションでの再開と同じセッションでの編集復帰を区別する。

### FR2 出力終了後に写真表示を復帰させる

- Given 記事画面で出力のため表示画像を解放した。When 出力が終了して同じ記事の編集・プレビュー画面を操作できる状態に戻る。Then 有効な記事に対して表示用画像の取得を再開し、取得可能な4枚を表示する。
- 正常完了、画像取得失敗、処理取消、保存先パネルの取消、表示解放後の容量不足・保存/入力検証失敗による早期終了を対象とする。表示解放前の確認取消では元の表示を維持する。
- 出力中に記事を離れた場合、旧記事の画像を再表示しない。出力結果・取消・復旧記録の判定を表示の再取得で上書きしない。
- 検証: 各終端に対し、実画像処理の終了と有効な記事を照合してから画像取得へ戻ることを確認する。遷移接続を通る回帰試験を含め、部品を直接生成する試験だけで代用しない。

### FR3 再試行を実際の画像取得につなげる

- Given 有効な記事に取得失敗または表示状態欠落の写真があり、出力や他の画像取得で操作を止める必要がない。When その番号の再試行を押す。Then 実際に取得を開始し、取得可能なら画像を表示する。
- 取得不能なら失敗を表示し、後に写真が利用可能になれば再試行で回復できる。操作できない間は理由が分かる状態表示と無効化を行い、押せるボタンを無反応にしない。
- マウスと既存のキーボード操作に同じ条件を適用する。通常の番号別再試行で他の画像・本文を消さない。
- 検証: 画像取得元の要求発行と画面状態の変化を確認する。状態文言やボタンの存在だけを成功根拠にしない。

## 非機能要件

全てMust。

### NFR1 本文・写真参照・プライバシーを保護する

表示の復帰・失敗・再試行で、保存済みと未保存の本文、日付・撮影情報、写真IDと順序を変更しない。既存の手動保存、離脱確認、保存形式、出力確定・所有確認・片付けを維持する。写真ライブラリの変更、ネットワーク画像取得、一般クリップボード操作、認可リセットを追加しない。自動試験は合成画像と所有する専用領域を使用する。

検証: 復帰前後の本文・順序の一致、未保存編集保持、既存の保存/出力回帰と専用データの片付けを確認する。entitlementsや通信方針を変更しないことを差分で確認する。

### NFR2 要求の世代・期限・資源制限を維持する

記事を離れたり切り替えた後の遅い旧応答が現記事を更新しない。退場後に旧記事の不要な表示要求・保持を残さず、再取得を重複開始しない。表示画像を解放する出力の意図を維持し、実際の出力画像処理が残っている間に表示取得を重ねない。既存の画像予算256MiB、表示要求の15秒の期限、出力の直列化を緩和しない。要求が完了しない場合も期限で失敗へ遷移する。

検証: 制御可能な遅延・取消・資源計測で旧応答拒否、退場後の解放、期限、出力との排他を確認する。出力終端の定義と再取得の所有者は実装計画で具体化する。

### NFR3 CI優先の回帰検証と実機確認を区別する

TDDで今回の接続不具合を先に再現し、修正前の意図した失敗と修正後の成功を記録する。既存スイートを維持し、統合前CIと全製品80%以上の行カバレッジを満たす。既存CIの結果はソース同一性を確認して利用し、同じ目的のローカルビルド・native/UI・性能試験を重複実行しない。

本人のMacでは最終段階に確認をまとめ、通常のXcode起動で「下書き再開→4枚表示→出力または取消→記事へ復帰→必要時の再試行→本文と写真順序の保持」を確認する。自動試験の成功と本人の実機での解消を別々に記録する。実機結果がない間は解消確認済みとしない。

## 制約・対象外

- 現在のSwiftUI/AppKit/Photos構成と本人Mac向け利用を維持する。新しい配布基盤や有料サービスは導入しない。
- 写真アプリでの事前読込後に成功した出力について、自動ダウンロードを追加しない。
- 記事生成機能追加、note自動連携、写真本体の恒久複製、認可・保存先の変更、VoiceOverの追加設計/検証、無関係な全面改修は対象外。
- 製品変更・具体的な試験構成は、要件承認後の実装計画で確定する。

## 確定事実と未観測の区別

仕様上の仮定を置いて修正範囲を広げていない。本人の正確な操作順と実行中の要求状態は未観測であり、静的に見つかった出力後の表示欠落が今回の唯一の原因とは断定しない。再現試験と最終実機確認で確かめ、別原因が見つかれば同じ要件に照らして対処する。

## 出典と対応

| 要件 | 出典 |
| --- | --- |
| FR1 | 本人の下書き復帰時の画像・再試行無反応の報告、初期依頼 |
